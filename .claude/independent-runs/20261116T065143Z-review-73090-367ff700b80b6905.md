## Findings by severity

### Critical

### Important

**1. The account-id scheme change silently orphans existing projection history and the cross-adapter `vendor_account` alignment, with no migration** — `src/unlimited/cache.py:93`, `src/unlimited/projection.py:51`, `src/unlimited/adapters/anthropic_console.py:6`

- Projection history is keyed by `_key(account, name)` (`src/unlimited/projection.py:51`), where `account` is now `person_org` instead of the bare `accountUuid`. On upgrade, every existing Anthropic entry becomes unreachable under the new keys, and `MIN_PAST = 3` (`projection.py:40`) means forecasts degrade from history-backed to guess for up to ~3 weeks per weekly window until past windows re-accumulate. The orphaned old-key entries are also never rewritten — `prune` keeps anything with `samples or past`, so they linger as dead weight.
- Related, same root: `anthropic` readings now emit `vendor_account = person_org` (`ACCOUNT_IS_VENDOR_ID = True`), while `anthropic-console`'s whoami still resolves to the bare `accountUuid` — so the two Anthropic surfaces no longer share the id the README says is used to "match readings taken elsewhere to this one" (`README.md:145`). No code joins them today, so the impact is confined to `unlimited accounts` output, but the invariant the docs promise is gone for this pair.
- Also orphaned: previously captured statusline files `~/.cache/unlimited/claude-statusline/<bare-uuid>.json` never match a discovered account again and are never cleaned.

**Why it matters:** it is a one-time, user-visible regression on upgrade that nothing in the diff or the PR body acknowledges. **Fix sketch:** on first sight of a composite id, carry history over from the bare-uuid key whose person matches (the person prefix is recoverable by splitting on `ORG_JOIN`); or prune the orphaned old-key history and statusline files once. If the design doc consciously accepted the reset, say so in the PR body instead — but I could not check the doc (external repo, see below).
